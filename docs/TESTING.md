# How we test

Every change goes through the same loop: build, test, deploy, check the live site, fix, improve, test again. A change is done when the live page behaves the way the pull request says it does.

### How CI is split
`.github/workflows/ci.yml` has these jobs on every pull request and push to main:
- `python` (20 minutes): validate, the Python tests, the rebuild with the generated-files diff, and the dash scan.
- `js` (30 minutes each): six shards, `shard: [1, 2, 3, 4, 5, 6]` (four until 2026-10-14). Each shard runs `node --test --test-concurrency=2 $(node tools/shard.mjs ${{ matrix.shard }} 6)`: `--test-concurrency=2` runs two test files at a time (so the 7 GB heap cap cannot be multiplied by three children on a 4 vCPU runner), and `tools/shard.mjs` prints the files for that shard. It lists the real `tests/*.test.mjs` on disk and packs them into shards by how long each file takes (greedy longest first, ties by file name, from `tests/test-weights.json`), so together the shards run every JavaScript test file exactly once and finish at about the same time. A new file with no recorded weight gets the median weight. Before 2026-10-15 the split was `--test-shard=N/6` by file position, which clustered the slow files (shards took 223 to 598 seconds). To refresh the weights after adding or changing slow tests, run the "Measure test file times" workflow by hand (`.github/workflows/test-weights.yml`: it times every file on a GitHub runner, two at a time with coverage on, like the shards) and commit the `tests/test-weights.json` it uploads. `node tools/time_tests.mjs` does the same on your own machine, but a busy laptop gives less even shards. To reproduce one shard locally, run `node --test --test-concurrency=2 $(node tools/shard.mjs 2 6)` (change the 2), and `node tools/shard.mjs 2 6` alone shows its file list.
- `check`: waits for `python` and `js` (`needs: [python, js]`, `if: always()`) and fails unless both succeeded. It is the one status check branch protection requires, so keep its name `check`. Do not add a required check for the shards.
- `coverage` (15 minutes, `needs: [js]`): downloads the V8 dumps every `js` shard uploaded (`coverage-v8-shard-N`, kept 3 days) into `coverage-v8/` and runs `tests/r3-tests-5-page-script-coverage-floor.test.mjs` on them, which checks the lib.js line floor and every page script floor. The suite runs once per push, in the shards. It is not part of `check` and not a required status check, so a floor failure shows as a red job on the run without blocking the merge button. The `js` job sets `NODE_OPTIONS=--max-old-space-size=7168` because dump collection raises memory use.
- `deploy` (10 minutes, `needs: [check]`): runs only on a push to `main`. It copies the site files into `_site`, uploads them with `include-hidden-files: true` (so `.well-known/security.txt` ships), deploys to GitHub Pages, then asks the live site for every page, `data/entries-lite.json`, `data/entries-home.json`, `data/meta.json`, `robots.txt`, `sitemap.xml` and `security.txt` and fails if one does not answer 200. A pull request never runs it. See `docs/RUNBOOK.md`, "How the site is published".

A test file is the smallest unit a shard can take, so a slow single file slows its shard. The two biggest sweeps are split by page: `tests/r2-tests-2-data-failure-find.test.mjs`, `-pages-a.test.mjs` and `-pages-b.test.mjs` (data failure sweep), and `tests/r2-tests-3-url-roundtrip-find.test.mjs`, `-permit.test.mjs` and `-calendar.test.mjs` (share-link round trip). Add a page to the file for its group; do not merge them back.

## Scheduled checks
Weekly link check, weekly Lighthouse check (`.github/workflows/lighthouse.yml`, assertions in `lighthouserc.json`), weekly mutation test of `assets/js/lib.js` (`.github/workflows/mutation.yml`, see below), monthly "needs a re-check" issue, CodeQL, and a daily date check (`.github/workflows/dates.yml`).

Set `DATE_CHECK_TODAY=utc` to make them use today in UTC. ## Mutation testing of lib.js
StrykerJS changes `assets/js/lib.js` in small ways (a flipped comparison, an emptied string, a removed branch) and reruns the tests; a change no test notices is a surviving mutant, a hole in the tests. It runs weekly (Sundays, `.github/workflows/mutation.yml`) and on demand (Actions, Run workflow); it is not part of `check`. The report is uploaded as the `mutation-report` artifact (`mutation.html`).

- Config: `stryker.config.json`. It mutates only `assets/js/lib.js` and runs 57 pure lib test files (files that load lib.js with no jsdom) through the tap runner, one `node --test-reporter=tap` process per file. Left out: files that load jsdom, files that measure the byte size or scan the source text of lib.js (`r1-perf-scale-1`, `r3-a11y-perf-29-first-load-code-bytes`, `r3-tests-2`, they fail on Stryker's instrumented copy), and files over about 900 ms (`r1-tests-5` has a wall-clock limit and a time-based seed; `r1-perf-scale-5`, `r1-tests-2`, `r1-tests-4-order-independence`, `r1-tests-5-rank-properties`, `r1-tests-5-text-and-suggestion-properties`, `r3-a11y-perf-4`, `r3-tests-2-clock-sweep` only slow the run). A new pure lib test file must be added to `tap.testFiles` to count; `tests/test_r3_tests_6_workflow_policy.py` checks that every listed file loads lib.js without jsdom.
- Four files, `tests/mut-a-lib.test.mjs` to `tests/mut-d-lib.test.mjs`, were written on 2026-10-15 to kill survivors from the first run (insights, grade phrases, blank counts, message splitting, relax helpers, ranking and sorting, ICS, dates and status). `tests/clock-label.test.mjs` pins `clockLabel` in `lib.js`: 24 is midnight, 12 is noon, and 21.5 reads as 9:30 p.m. They are all in `tap.testFiles`.
- Measured 2026-10-14, before those files were added: mutation score 81.55 percent (3,367 mutants: 2,732 killed, 9 timed out, 604 survived, 16 no coverage, 6 errors). About 28 minutes on a 14 core Mac with 4 workers. Most survivors are string labels and region and city tables, which only the jsdom page tests read.
- Measured 2026-10-15 in CI (run 38780513573), after the `mut-a..d` and `clock-label` files: mutation score 95.3 percent (3,458 mutants: 3,140 killed, 149 timed out, 156 survived, 7 no coverage, 6 errors). Most of the survivors left were judged equivalent by the agents that wrote those tests.
- Measured 2026-10-17 in CI on main (run 39006683106), after the place changes of 2026-10-15: mutation score 98.06 percent (3,465 mutants: 3,084 killed, 308 timed out, 60 survived, 7 no coverage, 6 errors). `tests/r10-tests-1-mut-lib-hours.test.mjs` then pinned the hours checker (no early-start, late-exception or weekly-cap line on a legal week, including limits written as null), the 21 day "closing soon" rank key, `clockLabel` minutes and the relax count for a place. Most of the survivors left are equivalent (a null limit already reads as no limit, a band label nothing looks up).
- Page scripts can be mutated too: `tests/dom-helper.mjs` shares Stryker's mutant switch with the jsdom window, so a run with `"mutate": ["assets/js/permit.js"]` and jsdom test files in `tap.testFiles` works. It is slow (several seconds a file per mutant), so it is not in the weekly run; pick a few test files for the script and leave out `StringLiteral` (`"mutator": {"excludedMutations": ["StringLiteral"]}`).
- `thresholds.break` is 93 (76 until 2026-10-15, 90 until 2026-10-17), five points under the measured score of 98, so the run fails only on a real drop. Raise it when the score rises; do not lower it to make a run pass.
- Run it: `npx stryker run` (needs `npm ci`; the HTML report is `reports/mutation/mutation.html`, and `reports/` and `.stryker-tmp/` are git-ignored). For a quick look use `npx stryker run --mutate "assets/js/lib.js:250-310"`.

## Checks a person does
jsdom does not draw anything, so layout and printing need eyes. Before a change to a page is called done, open the live page at a phone width (390 pixels) and a desktop width, look for text that overflows, and try the main action once. The pre-promotion checklist is in `ROADMAP.md`.

## Where the tests live
All test files are in `tests/`.
- `tests/test_*.py` are Python `unittest` tests. Most test the tools in `tools/`. `test_docs_sync.py` and `test_workflows.py` test the docs and the workflow files.
- `tests/*.test.mjs` are Node tests that use `node:test`. `tests/lib.test.mjs` tests `assets/js/lib.js` with no browser.
- Files ending in `.dom.test.mjs` load a built page in jsdom, with its real scripts, through `tests/dom-helper.mjs`.
- Interview tests are pre-woken: `loadPage("interview.html")` fires `focusin` on `#availability`, so `permits.json` loads as it would for a teen using the hours checker. Pass `lazy: true` to test the cold first visit, where `permits.json` must not load. `tests/interview.dom.test.mjs` has one such cold-load assertion, and `tests/r2-a11y-perf-4-interview-lazy-permits.test.mjs` covers the lazy path in detail.
- Files with `r1-`, `r2-` or `r3-` in the name were added in review rounds. The area comes right after the round prefix, and a number ends the name, optionally followed by a short label such as `-ics-fold`. The `.mjs` areas are `a11y-perf`, `accuracy`, `data-content`, `docs-ops`, `handout`, `oc`, `perf-scale`, `ranking-ux`, `teen-flow` and `tests`. The Python files use underscores, for example `test_r1_data_hygiene_2.py`.
- Rounds 4 and later follow the same rule (`r4-`, `r5-` and so on, any round number). Three older round 4 files do not follow it yet: `r4-share.test.mjs`, `r4-states-1.test.mjs` and `r4-tiles.test.mjs`. They are listed with reasons in `LEGACY_NAMES` in `tests/test_r2_tests_6_suite_guard.py`, and the guard fails if one of them is renamed to the rule or deleted without removing its entry.

The toolchain is pinned. `.nvmrc` holds the Node version (22.22 or newer; `package.json` `engines` says the same) and every workflow that sets up Node reads it with `node-version-file`. `requirements-dev.txt` pins `jsonschema` and its dependencies to exact versions; install them with `pip install -r requirements-dev.txt` (CI does the same). `tests/test_r3_tests_6_workflow_policy.py` checks all of this, and Dependabot watches the pip file monthly. Every GitHub Action is pinned to a full commit SHA with the version tag in a trailing comment (for example `# v7`), every checkout sets `persist-credentials: false`, `ci.yml` and `codeql.yml` cancel superseded runs for pull requests only, and Dependabot groups the Actions updates into one pull request after a 7 day cooldown; the same test file checks each of these. `package.json` has an `overrides` entry that pins `qs` to 6.16.0. `qs` is a test-only dependency: `@stryker-mutator/core` pulls it in through `typed-rest-client`, which asks for an older version. Nothing from `node_modules` reaches the site.

To run one file:

```bash
node --test tests/lib.test.mjs
python3 -m unittest tests.test_tools -v
```

The Home picker budget: after a pick, `tests/r3-a11y-perf-2-home-four-files.test.mjs` checks the four cards come from `data/programs/<id>.json` (under 20000 bytes in all), never from the big shared files. `data/programs` is published with the site and is not in `.gitignore`. The deploy job's rsync also excludes `stryker.config.json`, `reports` and `.stryker-tmp`, so mutation-testing files never reach the live site.

The Numbers page budget: `tests/r3-a11y-perf-6-insights-stats-file.test.mjs` checks `insights.html` reads `data/entries-stats.json` (same ids and order as the entries file, only the keys `lib.insights()` reads, null values left out) and never the card file, and that every number on the page matches `L.insights` run on the full data. `tests/test_r3_tools.py` checks the file is a projection of `entries.json` and under 60 percent of the card file.

## First-load weight ceilings
The size limits in `tests/r1-perf-scale-1.test.mjs` are the phone-weight ceilings. The first-load data per page is in `tests/r3-a11y-perf-15-first-load-data-inventory.test.mjs`: Home reads `data/entries-home.json` (ceiling 920,000 bytes), Numbers reads `data/entries-stats.json` (ceiling 827,500) and Ages 12 to 14 reads `data/entries-core.json` and `data/younger.json` (ceiling 1,100,000). Code weight per page is in `tests/r3-a11y-perf-29-first-load-code-bytes.test.mjs`. A limit may go up only when a person approves the extra weight for phone users, and the approval is written in the pull request and in the comment above that limit. Adding data cards is not a reason to raise a limit by itself: slim the entries first, or get the approval. Limits raised on 2026-10-11 for ticket p7-regions-1 and again on 2026-10-12 for the city data waves (2,214 programs) are marked pending approval in that file until one is recorded. The same "PENDING PERSON APPROVAL" note is on the rows raised on 2026-10-14 and 2026-10-15 (phone layout, build-time tiles and accessibility fixes), and on 2026-10-18 for the issue 19 Southern California cards (2,686 programs), and on 2026-10-17 for the Southern California, Santa Barbara and Merced cards, in `tests/r1-perf-scale-1.test.mjs`, `tests/r3-tests-4-size-ratchet.test.mjs` and `tests/r3-a11y-perf-29-first-load-code-bytes.test.mjs`. No person has recorded an approval yet, so do not raise those rows again without one.

Phone layout has no jsdom test of how it looks, so check it by eye (see "Checks a person does"). The CSS and markup rules are in `docs/MAINTAINING.md`, "Phone layout". The axe sweep (`tests/a11y-axe.dom.test.mjs`) and the weekly Lighthouse check cover what they can.

Collapsed things are not tab stops: `tests/r1-a11y-perf-7-collapsed-not-tabbable.test.mjs` loads Home, Find, Playbook and Ready at 390 pixels (phone query mocked) and checks the Menu starts closed with the nav hidden, opens, and closes on Escape with focus back on the button.
